# Track Review: Filter Service Test Coverage

**Review date:** 2026-07-09  
**Reviewer:** Measure daily automation  
**Commit reviewed:** `1b146993` — split deferred server-service test coverage into 3 tracks

---

## Summary

The track proposes adding unit tests for `FilterService`, claiming it has no dedicated coverage. A comprehensive `FilterService.test.ts` already exists with ~28 tests covering CRUD operations, validation, `applyToSeries`, and `applyToIndexers`. The track is therefore not green-field work; it should be reframed as a coverage audit. Additionally, the spec's acceptance criteria mention "quality, language, size, indexer, and custom-format filter paths," but the actual `FilterService` does not implement quality/language/size/custom-format evaluation — its fields are `monitored`, `network`, `genre`, `tag`, `rating`, `status` (series) and `protocol`, `enabled`, `capability`, `priority`, `tag` (indexers). This mismatch needs correction before execution.

---

## Spec Alignment

**Verdict: partial**

- **Missed:** The claim that `FilterService` has "no dedicated unit-test coverage" is incorrect. `server/src/services/FilterService.test.ts` already exists and tests:
  - `list`, `create`, `update`, `delete` with Prisma mocked.
  - Validation errors for invalid conditions and empty names.
  - `applyToSeries` with `and`/`or` operators, empty conditions, rating comparisons, genre contains, network equals, and ratings-object handling.
  - `applyToIndexers` with enabled, protocol, capability, priority, tag-from-settings-JSON, and malformed-JSON handling.
- **Partially met:** The acceptance criteria correctly call out positive/negative matches, composite AND/OR logic, and unknown filter types. The existing tests cover AND/OR and some validation of invalid conditions, but do not explicitly test unknown filter *types* or negative matchers such as `notEquals`/`notContains`.
- **Misaligned:** The criteria list "quality, language, size, indexer, and custom-format filter paths." The current `FilterService` source defines no `quality`, `language`, `size`, or `custom-format` fields or evaluation logic. "Indexer" is partially covered via `applyToIndexers`. This acceptance criteria appears to describe a different or aspirational filter model, not the implemented service.

---

## Plan Quality

- **TDD adherence:** Phases 2–5 assume starting from zero tests. Because a test file already exists, the red/green cycles should be reframed around identified coverage gaps rather than the full service surface.
- **Scope clarity:** The plan is coherent for a fresh service, but it will duplicate existing work if followed literally. It lacks a phase to review the existing test file and coverage report.
- **Commit messages:** Suggested commits (`test(server): add red tests for FilterService`) are inaccurate given the existing tests.
- **Typecheck note:** The spec mentions documenting "pre-existing strict-mode type errors in the affected test file." `tech-debt.md` already flags 23 pre-existing strict-mode errors including `FilterService.test.ts`; this is a useful acceptance criterion.

## Recommended Next Actions

2. Run the existing `FilterService.test.ts` suite with coverage and record the current branch-coverage percentage.
3. Update the spec acceptance criteria to match the actual `FilterService` API:

5. If coverage is below 80%, enumerate the uncovered branches and add only the missing tests, using the existing `makePrismaMock` helper and test structure.
