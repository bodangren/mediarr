# Track Review: Subtitle Services Test Coverage

**Review date:** 2026-07-09  
**Reviewer:** Measure daily automation  
**Commit reviewed:** `1b146993` — split deferred server-service test coverage into 3 tracks

---

## Summary

The track proposes adding dedicated unit tests for `SubtitleNamingService`, `SubtitleRequirementEngine`, and `SubtitleProviderFactory`, claiming they currently have no coverage. In reality, all three services already have substantial `.test.ts` files in `server/src/services/`. The new track is therefore largely redundant and out of sync with the current codebase. It should be re-scoped from "create tests" to "audit and, if necessary, harden existing coverage" rather than proceeding as written.

---

## Spec Alignment

**Verdict: missed**

- The spec's opening claim — "Three server-side subtitle services currently have no dedicated unit-test coverage" — is factually incorrect.
- Existing test files:
  - `server/src/services/SubtitleNamingService.test.ts` — 18 tests covering path construction, forced/HI suffixes, extension handling, language lowercasing, variant-token sanitization, collision handling, and subtitle-directory override.
  - `server/src/services/SubtitleRequirementEngine.test.ts` — ~27 tests covering missing/satisfied logic, cutoff handling (`ANY_CUTOFF_ID` and specific IDs), audio exclude/include rules, forced/HI flags, language normalization, and `computeByVariant`.
  - `server/src/services/SubtitleProviderFactory.test.ts` — 9 tests covering provider registration, `resolveAllManualProviders`, explicit/config-based provider resolution, lowercase normalization, and unsupported-provider errors.
- The archived parent track (`chore_untested_server_services_20260526/plan.md`) explicitly documents this: an S7 override dated 2026-06-13 states `SubtitleNamingService` tests were completed externally at `5aa6ee7` and are GREEN.
- The acceptance criteria list test categories that are already covered by the existing suites (filename construction, language ordering/tag sanitization, requirement rules, provider resolution, fallback behavior, unsupported-language handling).
- The spec does not mention an 80% branch-coverage baseline, current coverage numbers, or any gap the track is meant to close.

---

## Plan Quality

The plan is well-structured for a *green-field* TDD effort (discovery → red → green → regression), but it is the wrong shape for the actual state of the code:

- **TDD adherence:** The plan assumes starting from zero tests. Because tests already exist, phases 2–5 would either duplicate existing work or create conflicts.
- **Commit granularity:** Suggested commit messages (`test(server): add red tests for SubtitleNamingService`) are misleading if the tests are already present.
- **Scope:** The plan does not include a coverage-audit or gap-identification phase, which is what the track actually needs.
- **Closeout:** Phase 6 correctly mentions updating `tech-debt.md` and `measure/tracks.md`, but without a clear success criterion beyond "tests pass".

## Recommended Next Actions

1. **Do not execute the plan as written.** Instead, treat this track as a coverage audit.
2. Run `cd server && bun run test -- SubtitleNamingService.test.ts SubtitleRequirementEngine.test.ts SubtitleProviderFactory.test.ts` and capture branch-coverage numbers.
3. Compare actual coverage against the 80% target. If all suites already meet it, close the track with a documentation-only update.

5. Update `measure/tech-debt.md` to reflect that the subtitle services are no longer untested, with a note about the audit date.
