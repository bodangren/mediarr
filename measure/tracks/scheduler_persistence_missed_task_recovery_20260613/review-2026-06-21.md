## 3. Code quality observations

- Clean dependency-injection design: `Scheduler` depends on a `SchedulerStateRepository` interface, not on `AppSettingsRepository` directly, satisfying the architecture guardrail.
- Advancing next-run in the `executeRecorded()` `finally` block prevents a failed cron tick from freezing the schedule.
- Tests reuse the existing `node-cron` mock pattern and fake timers for deterministic assertions.
- Repository writes in `schedule()` and `stop()` are fire-and-forget; failures are logged but do not block scheduling semantics. Consider surfacing write failures more explicitly if operational observability requires it.
- The `SchedulerStateRepository` interface currently lives in `Scheduler.ts`; ensure it is exported when the real repository implementation is added in a separate file.

## 4. Risks / blockers

- **Main risk:** Phases 3–5 are unimplemented, so the track cannot be closed yet.
- **Schema migration missing:** the strategy calls for a `schedulerState` JSON column on `appSettings`. Until that migration exists, the real repository cannot be wired.
- **No integration coverage yet:** current tests use an in-memory mock repository. The "restart" persistence claim will not be proven until Phase-3 integration tests verify a second `Scheduler` instance reads the same store.
- **`Scheduler.start()` does not exist yet:** this method must be added and called from `main.ts` after all `schedule()` calls.
